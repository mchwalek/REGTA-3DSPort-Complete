# reLCS 3DS build

This repo is NOT self-contained: the devkitARM SDK and host packaging tools
live outside `repo/`, at the workspace root. `$WORKSPACE_ROOT` is the parent
directory containing `repo/`, `sdk-r55/`, and `hosttools/` (set it in your
shell, not in this repo).

## Required environment (every build/package command)

```sh
export DEVKITPRO=$WORKSPACE_ROOT/sdk-r55
export DEVKITARM=$DEVKITPRO/devkitARM
export PATH="$DEVKITARM/bin:$DEVKITPRO/tools/bin:$PATH"
```

`common/devkitarm-r55.mk` hard-errors unless `arm-none-eabi-gcc` reports
exactly `10.2.0` AND `devkitARM release 55` — a generic ARM GCC 10.2 will not
work. Without the exports above, `scripts/build.sh` defaults `DEVKITPRO` to
`/opt/devkitpro`, which does not exist in this environment, and fails with a
confusing error from `devkitarm-r55.mk`, not a clear "compiler missing"
message.

## Full build

```sh
DEVKITPRO=$WORKSPACE_ROOT/sdk-r55 DEVKITARM=$WORKSPACE_ROOT/sdk-r55/devkitARM \
  $WORKSPACE_ROOT/repo/scripts/build.sh relcs
```

Aliases accepted: `lcs`, `stories`. This runs
`make -C stories/build -f GNUmakefile LOADING_PIPELINE=1 BOTTOM_LOADING=1 BOTTOM_RADAR=1`.
Outputs: `stories/build/relcs.elf` (~58 MB), `relcs.3dsx` (~4 MB), `relcs.lst`,
`.map` (literally named `.map` — a makefile quirk, not a typo).

Clean build takes ~1 minute on a 20-core machine. It is never a true no-op:
`src/extras/GitSHA1.cpp` is regenerated by `printHash.sh` on every invocation,
which relinks the ELF/map/lst/3dsx even with no source changes.

## THE FLAG-CONSISTENCY TRAP

All three games (`III`, `miami`, `stories`) fingerprint their object
directory by the exact `-D` flag set: `PREFIX := ./obj/$(FINGERPRINT)/`,
where `FINGERPRINT` is an md5 of the concatenated `RE3_CFG`/`LIBRW_CFG`/
`MPG123_CFG`/`DEBUG`/`OPTFLAGS` strings — identical scheme in all three
`GNUmakefile`s. **A differently-flagged build can never silently reuse
another build's objects** — different flags hash to a different
`obj/<fingerprint>/` and rebuild from scratch there. (Earlier guidance here
claimed `stories`'/`miami`'s `obj/` was flat and unfingerprinted unlike
III's — verified false by reading all three `GNUmakefile`s side by side;
there is no flat `obj/src/...` rule in any of them, only
`$(PREFIX)src/%.o: ../src/%.cpp`.)

The real trap is narrower but still real: the **final binary name is not
fingerprinted** (`$(TARGET).elf`/`.3dsx`, `TARGET := relcs`). A bare `make
-C stories/build -f GNUmakefile` with no `LOADING_PIPELINE=1
BOTTOM_LOADING=1 BOTTOM_RADAR=1` computes a different, all-defaults
fingerprint, builds a clean (not mixed) but **feature-flag-incomplete**
object set in that other `obj/<fingerprint2>/`, and links it into the
*same* `relcs.elf`/`relcs.3dsx` output path — silently overwriting a
correctly-flagged build with one missing the 3DS-specific loading
pipeline/bottom-loading/bottom-radar code. Always use `scripts/build.sh
relcs` or pass the identical flag set by hand. `make -C stories/build -f
GNUmakefile clean` removes the currently-fingerprinted `obj/` subtree for
whatever flags you pass it with — a safe way to force a from-scratch
rebuild if you suspect a stale object (clean only the tree you're
rebuilding — do not touch III/miami's `build/` dirs unnecessarily).

## Single-file compile (fast iteration / syntax check)

Object paths live under the flag-dependent `obj/<fingerprint>/` (see
above) — there is no rule for a flat `obj/src/...` path, so don't guess it
by hand (deleting a stray flat `obj/src/....o` left over from an older
checkout and rebuilding it will fail with "No rule to make target", which
is the tell that you're looking at the wrong path). Discover the real path
for your flags with `object-info`, then build that exact target:

```sh
make -C $WORKSPACE_ROOT/repo/stories/build -f GNUmakefile \
  LOADING_PIPELINE=1 BOTTOM_LOADING=1 BOTTOM_RADAR=1 \
  object-info | grep BottomScreen3DS
# -> 	 ./obj/<fingerprint>/src/core/BottomScreen3DS.o

make -C $WORKSPACE_ROOT/repo/stories/build -f GNUmakefile \
  LOADING_PIPELINE=1 BOTTOM_LOADING=1 BOTTOM_RADAR=1 \
  obj/<fingerprint>/src/core/BottomScreen3DS.o
```

Add `-n` to the second command to preview the exact compiler invocation
without running it. Force recompilation of one file with `-W
../src/core/Foo.cpp`. `source-info` lists every compiled source file the
same way, if you need to confirm a file is actually part of the build.

## Packaging a .cia

`scripts/package-cia.sh [re3|revc|relcs ...]` (aliases `iii`/`vc`/`lcs`/
`stories` accepted, same as `build.sh`) wraps
`packaging/production_cia/build_production.sh` (a portable, table-driven
bash script over re3/revc/relcs) and defaults `BANNERTOOL`/`MAKEROM`/
`THREEDSXTOOL` to the vendored `$WORKSPACE_ROOT/hosttools/`/`sdk-r55/`
locations, so no env vars are required in the common case:

```sh
scripts/package-cia.sh relcs
```

Omit the game argument to package all three (each requires its own ELF to
already be built). Override any of `BANNERTOOL`/`MAKEROM`/`THREEDSXTOOL` by
exporting them before calling the script if the vendored copies aren't
where expected. Output lands in `packaging/production_cia/output/`
(gitignored): `GTALCS For Nintendo 3DS.3dsx` and `.cia`, plus intermediate
`.bnr`/`.smdh`.

Known-good relcs CIA sha256 (from the 3DS menu accept/cancel remap commit
`f1ae416`) for sanity-checking that packaging still works end-to-end:
`f852b41abf69d8a69c3e493f91dc863581d78f0a4a29cac71df555b545362122`. A
different hash after a source change is expected and correct; use this only
to confirm the packaging pipeline itself still runs and produces a similarly-
sized artifact, not as an exact-match regression test.

## Deploying to a real 3DS over the network (3dslink)

`$DEVKITPRO/tools/bin` does **not** ship `3dslink` (only `3dsxdump 3dsxtool
bin2s bmp2bin generate_compile_commands mkromfs3ds padbin picasso raw2c
smdhtool`). If `$WORKSPACE_ROOT/hosttools/3dslink` doesn't already exist,
build it — it's a tiny host tool (zlib is its only dependency) with no
autotools output committed, so a plain autoreconf/configure won't work
out of the box:

```sh
git clone --depth 1 https://github.com/devkitPro/3dslink.git /tmp/opencode/3dslink
gcc -O2 -std=gnu99 -DPACKAGE_STRING='"3dslink 0.6.3"' \
  -o $WORKSPACE_ROOT/hosttools/3dslink \
  /tmp/opencode/3dslink/host/src/main.c -lz
```

(`PACKAGE_STRING` is normally generated by `configure` from `configure.ac`'s
`AC_INIT` version; defining it by hand skips the whole autotools step.)

Usage — the 3DS must already be sitting in Homebrew Launcher (or another
netloader-capable app) waiting for a connection; it listens on TCP/UDP 17491:

```sh
scripts/deploy.sh relcs <3DS-LAN-IP>
```

(`<3DS-LAN-IP>` defaults to `$N3DS_IP` if omitted.) This wraps
`$WORKSPACE_ROOT/hosttools/3dslink -a <ip> stories/build/relcs.3dsx` with a
build-output existence check. For an upload that keeps streaming the
console's stdout/stderr afterward, call `3dslink` directly with `-s`.
**Do not wrap either in a short Bash timeout** — a ~4 MB `.3dsx` over Wi-Fi
takes noticeably longer than a quick command, and killing the transfer
mid-upload leaves the console in a bad state (it may boot the partial app
or drop out of listening mode), requiring the user to relaunch Homebrew
Launcher on-device before the next attempt.

**A captured Bash tool run of `scripts/deploy.sh`/`3dslink` showing progress stuck at
some percentage (e.g. `"... sent (48.92%), 189 blocks"`) with no further
output is expected, not a sign of a stalled/failed transfer.** `3dslink`
renders its progress bar with carriage returns (`\r`), overwriting the same
terminal line in place; a tool that snapshots captured output rather than a
live terminal can end up showing only one such overwritten frame even though
the process went on to finish normally and already exited. Confirm via
`pgrep -af 3dslink` — if no `3dslink` process is running anymore, the
transfer already completed (or failed) and isn't still in flight; the
percentage in the captured text is not meaningful once the process has
exited. The only reliable way to know if the deploy actually worked is to
ask whether the app launched on the console — don't re-run `scripts/deploy.sh`
speculatively based on a stale percentage, since that risks compounding a
genuinely bad console state if the first attempt is in fact still live.

## Verification after a build/packaging change

```sh
python3 -m unittest discover -s $WORKSPACE_ROOT/repo/scripts/tests -p 'test_*.py'
$WORKSPACE_ROOT/repo/scripts/verify-layout.sh
```

`test_3ds_world_and_menus.py`'s `test_compiled_menus` needs `DEVKITARM`
exported (see above) — it defaults to a `toolchains/devkitARM-r55` path that
does not exist in this environment.

## A new `gamefiles/<game>/` override needs its install-manifest entry too

`scripts/verify-layout.sh` checks two independent things, and passing the
first doesn't mean the second passes: source-tree symlinks, and
`common/3ds/InstallManifest.h` (a checked-in, non-gitignored generated
header with a per-file `{path, size, sha256}` entry for everything under
each game's `gamefiles/<game>/`, read at runtime by
`RegtaInstall::validate()` in `common/3ds/GameInstallation.h` before the
game boots — a mismatch makes the game show an install-error screen and
exit, not crash loudly). Adding a *new* `gamefiles/relcs/...` runtime
override file (per the two-edit pattern in `AGENTS.md` landmine #5) also
needs:

```sh
python3 scripts/tools/generate_install_manifest.py
```

run and committed, or `verify-layout.sh` silently starts failing on the
*next* full check even though the override itself is wired up correctly.
This was the root cause of a "the game quits shortly after booting"
regression during a WEAPON.DAT override — the new file was correctly
gitignore-allowed and copied by `setup-game.sh`, but the manifest wasn't
regenerated, so the on-device/emulator install check failed on a file the
override added.

**Separately:** `3dslink` only pushes the `.3dsx` binary — it never pushes
new or changed SD-card data files (`AGENTS.md` landmine #14 territory, but
worth restating for `gamefiles/` overrides specifically). After adding or
changing any `gamefiles/<game>/` override, re-run
`scripts/setup-game.sh <game> <original-data-dir> <sd-target-dir>` to
refresh the local SD staging directory (e.g. `sdstage/`) — a `3dslink`
deploy alone will boot a binary that expects the new override data but
never received it.
